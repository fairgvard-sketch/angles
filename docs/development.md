# Разработка сайта и кабинета

Сверено с `package.json`, сборочными скриптами и Vite-конфигурацией 13.09.2026.
POS и backend: [инструкция Kassa](../../kassa/docs/development.md).

## Рабочая копия и конфигурация

Для работы со всей системой расположите `anglesite/` и `kassa/` рядом.
Используйте Node.js 22 и lock-файлы (`npm ci`). Команды ниже выполняются
из `anglesite/`; отдельного `package.json` у кабинета нет.

Локальный `.env` в корне (секреты не коммитить):

```env
VITE_SUPABASE_URL=https://<test-project-ref>.supabase.co
VITE_SUPABASE_ANON_KEY=<public-anon-key>
VITE_PUBLIC_MENU_ORIGIN=http://127.0.0.1:5174
VITE_SITE_ORIGIN=http://127.0.0.1:8001
```

Первые две переменные задают Auth/API. Последние две переопределяют гостевые
ссылки и адрес фоновых изображений; без них код использует production-origin.
Они не переключают сам Supabase. В обоих репозиториях для одного стенда
должны быть URL и публичный ключ одной **тестовой** базы.

Все `VITE_*` доступны браузеру. `service_role`, пароли SMTP и провайдеров
сюда не помещать. Не выводить содержимое реального `.env` в отчёты.

## Сайт и полная сборка

```bash
npm ci
npm run build
python3 -m http.server 8001 --directory dist
```

Сайт: `http://127.0.0.1:8001/`. Кабинет: `http://127.0.0.1:8001/account/`.
`scripts/build-site.mjs` пересоздаёт `dist/`, собирает landing из
`ANGLE Landing Page.dc.html`, копирует login, демо и необходимые изображения.
Затем Vite собирает кабинет. Не хранить ручные правки в `dist/`.

## Быстрая разработка кабинета

```bash
npx vite --config backoffice/vite.config.js --host 127.0.0.1 --port 5173 --strictPort
```

Открыть `http://127.0.0.1:5173/account/`. Этот сервер предназначен для React-
кабинета, а не всей landing-страницы. Для проверки сайта и его статических
ресурсов используйте полную сборку выше.

Для гостевых страниц в другом терминале, из `kassa/`:

```bash
npm ci
npm run dev:menu -- --host 127.0.0.1 --port 5174 --strictPort
```

Открывайте ссылки `/order/<test-location-id>` и `/reserve/<test-location-id>`
из кабинета. Эти ID должны принадлежать тестовой базе. Тесты, создающие
организации, заказы, брони или смены, не запускаются на живых клиентах.

## Проверки

```bash
npm test            # unit + браузерные наборы
npm run build
npm run check:docs
```

`npm test` — это `test:unit` (логика и рендер в Node) и следом `test:browser`
(наборы `backoffice/test/*.test.mjs` в настоящем Chrome). Команды доступны и
по отдельности; у обеих задан `--test-timeout`, поэтому зависший тест
завершается ошибкой, а не ждёт бесконечно.

Браузер обязателен по умолчанию. Если Chrome не запускается, прогон падает с
причиной и ненулевым кодом — «зелёного» результата без браузера больше нет:

```
no browser for puppeteer (<причина>); установите браузер: npx puppeteer browsers install chrome
Браузерные наборы обязательны. Осознанный пропуск: ANGLE_BROWSER=optional (в CI не используется).
```

Установка браузера (требует сети, после неё нужен повторный прогон):

```bash
npx puppeteer browsers install chrome
```

Режимом управляет `ANGLE_BROWSER`: пусто или `required` — обязательный,
`optional` — осознанный локальный пропуск (`npm run test:no-browser`).
Любое другое значение — ошибка, чтобы опечатка не превратилась в тихий пропуск.
В режиме `optional` браузер всё равно запускается, если доступен. Если запуск
не удался, наборы отмечаются строкой `SKIP no browser for puppeteer`, и итог
несопоставим с полным: сравнивайте число выполненных тестов.
Запуск и остановка браузера живут в `backoffice/test/browser-harness.mjs`;
там же закрытие Chrome и локальных HTTP-серверов. Браузер связан с процессом
теста через stdio, поэтому снятый по таймауту прогон не оставляет осиротевший
Chrome. Отдельные наборы `puppeteer.launch` не вызывают — это проверяется
тестами `backoffice/test/browser-harness.test.mjs`, включая отрицательный:
недоступный Chrome обязан валить прогон.

Те же проверки выполняет CI (`.github/workflows/ci.yml`) на каждый push и PR:
Node.js 22, `npm ci`, установка Chrome, `test:unit`, `test:browser` с
`ANGLE_BROWSER=required`, `build`, `check:docs`. Деплоя в этом workflow нет.
CI работает с заглушками данных и локальным сервером; ключи и живые данные
не используются, для сборки задаются плейсхолдеры `VITE_SUPABASE_*`.

При падении браузерной проверки сообщение содержит состояние страницы:
открыт ли слой, где фокус, идут ли кадры, видима ли вкладка и были ли ошибки
скрипта. Это факты о причине, а не «ожидание истекло»: прежде чем считать
набор нестабильным, прочитайте их — состояние вида «слой открыт, фокус остался
снаружи, кадры идут» означает дефект приложения, а не теста.

Браузерные наборы проверяют кабинет на подставных данных. Они не проверяют
доставку Auth-писем, production SMTP, RLS реального сервера и печать.
Зелёный CI подтверждается только запуском CI, а не локальным прогоном.

Для правок QR-настроек короткий регрессионный прогон:

```bash
ANGLE_BROWSER=required node --import ./backoffice/test/register.mjs --test --test-timeout=60000 backoffice/test/qr-channel-state.test.mjs
```

Набор монтирует настоящий QR-раздел в React StrictMode с подставным Supabase
transport: повтор загрузки, поздние save/rollback/slug после смены точки или
канала, возврат A → B → A и обычное сохранение с повторным чтением.
Также проверяется Menu-only: без управления заказами/столами, но с общим QR,
ссылкой и рабочим сохранением оформления. Гостевой iframe подменяется,
внешние запросы перехватываются. Ширины
1280/375/320 проверяются для ошибки загрузки и Menu-only; это не полная мобильная приёмка.
Набор автоматически входит в `test:browser`; production SQL/API и гостевой
сценарий этими проверками не подтверждаются.

`check:docs` проверяет ссылки и полноту индекса только управляемого набора
документации; границы проверки описаны в [правилах](documentation-policy.md).
Шаг `check:docs` в CI ожидает, что рабочие документы из индекса закоммичены
вместе с кодом: файл из индекса, оставшийся в рабочем дереве, даст ошибку.

## Работа над изменением

Для изолированной проверки «счёт → тестовая оплата → подписка → доступ»
используется [локальный billing lab](../../kassa/docs/billing.md).
`scripts/billing-lab.mjs` не входит в сборку сайта и не публикуется.
Он создаёт отдельную БД из локальной схемы/технических справочников, без
production-ключей и клиентских данных. Auth в стенде синтетический;
GoTrue/PostgREST и SMTP проверяются отдельным Auth lab ниже.

1. Найти сценарий в [плане](product-completion-plan.md) и существующую
   реализацию в [карте системы](system-overview.md).
2. Если меняется RPC/схема — внести новую миграцию в Kassa и проверить оба
   клиента; применённые миграции не переписывать.
3. Проверить успешный путь, ошибки, повтор действия и отсутствие доступа.
4. Обновить связанный справочник, критерий приёмки и запись в
   [журнале](verification-log.md). Не выдавать локальный тест за production.
5. Для выпуска использовать [release checklist](release-checklist.md).

Recovery и подтверждение почты реализованы локально в A1–A3. Точные адреса
и сценарии живой приёмки — в [справочнике аккаунта](account-access.md).
Разрешённый redirect и зелёные SDK-тесты не подтверждают доставку письма.

## Локальная приёмка Auth и подписки

Опциональный интеграционный прогон, **не часть обычного `npm test` или CI**:
требует локальный Docker через Unix socket и уже подготовленный Supabase Kassa
(`supabase_db_kassa`, `supabase_auth_kassa`, `supabase_rest_kassa`). Не запускать
`db reset` ради этого теста. Допустимые baseline/образы закреплены в
[`scripts/auth-lab.mjs`](../scripts/auth-lab.mjs); список проверенных миграций
общий с billing/HTTP lab — [`lab-migrations.mjs`](../scripts/lab-migrations.mjs).
Сейчас лаборатории создают схему 169; неизвестные версии требуют review.

```bash
docker pull axllent/mailpit:v1.31.1
ANGLE_BROWSER=required npm run test:auth:lab -- angle_auth_lab_run_20260913
```

Каждому прогону — **новое** имя `angle_auth_lab_<suffix>` (строчные латинские
буквы, цифры, `_`). Повтор имени завершается отказом, не очисткой данных.
Из исходной локальной БД копируются только схема и явно перечисленные
технические справочники/история миграций. Миграции выбираются по точным
reviewed-именам; копии файлов с суффиксом ` 2` не применяются.

Стенд создаёт отдельную БД на локальном Postgres и отдельные контейнеры
GoTrue/PostgREST/Mailpit на существующей локальной сети Supabase. Это не
отдельная VM и не проверка полной связки Kong/Storage/Realtime. Новый случайный
JWT-ключ, SMTP только в Mailpit без relay, HTTP-порты только `127.0.0.1`.
`.env` не читается; production Auth/SMTP/checkout не меняются. Браузерный
прогон запрещает внешние запросы и создаёт только `@example.test` владельцев.

Реальный кабинет проходит регистрацию/письма, recovery, создание заведения,
форму счёта и обновление доступа после **серверной имитации** оплаты.
Сумма берётся из сохранённого счёта; платёжный ключ не выдаётся браузеру.
Сценарии и ограничения — в [справочнике аккаунта](account-access.md).

Прогон ограничен четырьмя минутами, Chrome обязателен. При завершении/обычной
ошибке/SIGINT/SIGTERM закрываются браузер, HTTP-сервер и только собственные
контейнеры. Синтетическая БД сохраняется для диагностики. При SIGKILL cleanup
не гарантирован: оператор сначала проверяет точные имена `angle-auth-*`,
не удаляет исходные `supabase_*` или чужие лаборатории. Если для работы
поднимали Colima, после неё вернуть исходное состояние.

Для ручной работы (тоже новая БД):

```bash
node scripts/auth-lab.mjs angle_auth_lab_manual_20260913
```

Команда печатает только локальные адреса кабинета/перехватчика и имя БД.
Использовать исключительно синтетические адреса/пароли; в ручном режиме
браузер не имеет запрета внешних переходов из тестового harness.
Не сохранять email-ссылки с токенами в отчёты. Standalone-режим не включает
платёжную симуляцию в UI; имитация подтверждения есть только в тестовом runner.

Конфигурация: [GoTrue](https://github.com/supabase/auth/blob/v2.192.0/README.md#configuration),
[Mailpit Docker](https://mailpit.axllent.org/docs/install/docker/),
[Mailpit API](https://mailpit.axllent.org/docs/api-v1/).
