# Аккаунт владельца и восстановление доступа

Сверено с кодом 13.09.2026. Область: `/account/` в ANGLE, задачи A1–A3
[плана завершения](product-completion-plan.md). Это не PIN-вход POS и не
уведомления гостям. Локальный путь через настоящий GoTrue, SMTP-перехватчик
и PostgREST проверен; настройки production Auth, внешняя доставка писем и
полная приёмка нового клиента пока **NOT RUN**. Результаты — в
[журнале проверок](verification-log.md).

## Пользовательские сценарии

- **Sign in**: email и существующий пароль. Новое ограничение длины не
  блокирует вход со старым шестисимвольным паролем.
- **Create an account**: новый пароль от 8 символов. Если сервер не вернул
  сессию, открывается **Confirm your email**, а не пустой кабинет.
- **Resend confirmation email**: повтор письма подтверждения. При ошибке
  `email_not_confirmed` этот путь доступен со страницы входа.
- **Forgot password?**: запрос ссылки без старого пароля. Ответ формы не
  раскрывает, зарегистрирован ли указанный email, и не доказывает доставку.
- Возврат по проверенной recovery-ссылке: два поля нового пароля,
  проверка совпадения, затем **Password updated**. Пользователь сам выбирает
  переход в кабинет или выход. Просроченная ссылка предлагает новое письмо.

Повторная отправка той же формы блокируется на время её запроса. Сетевые
ошибки обрабатываются, кнопки освобождаются после завершения запроса.
Сообщения сервера не выводятся в UI дословно. Серверная политика паролей
остаётся обязательной и может быть строже клиентского минимума.

## Настройки Supabase Auth перед живой приёмкой

Это инструкция оператору, не утверждение, что настройки уже выставлены.
Изменение production, создание настоящих пользователей и отправка писем
требуют отдельного согласованного прогона.

1. Проверить email/password provider и **Confirm email**. При отключённом
   подтверждении сервер может сразу вернуть сессию; UI следует этому ответу.
2. Проверить Site URL и явно разрешить нужные адреса возврата в Redirect URLs:

   | Назначение | Production | Пример локального Vite |
   |---|---|---|
   | Подтверждение | `https://angle.co.il/account/?auth=confirm` | `http://127.0.0.1:5173/account/?auth=confirm` |
   | Восстановление | `https://angle.co.il/account/?auth=recovery` | `http://127.0.0.1:5173/account/?auth=recovery` |

   Форма строит адрес на **текущем origin** и фиксированном `/account/`.
   `localhost`, другой порт, preview и другой домен — отдельные адреса,
   если они используются. Не включать широкую маску production-доменов.
3. Проверить шаблоны Confirm signup и Reset password. Стандартная ссылка
   `ConfirmationURL` должна сохранять запрошенный redirect. Пользовательский
   шаблон, отправляющий только на Site URL, нужно отдельно сверить: смена
   настройки allowlist сама по себе такой шаблон не исправляет.
4. Проверить настроенный SMTP, отправителя, ограничения отправки и доставку
   на тестовый адрес владельца, включая spam. Наличие API-ответа без ошибки
   не является подтверждением доставки.

Правила адресов и шаблонов: [Supabase Redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls).
Запрос восстановления: [resetPasswordForEmail](https://supabase.com/docs/reference/javascript/auth-resetpasswordforemail).
Настройка password Auth и почты: [Password-based Auth](https://supabase.com/docs/guides/auth/passwords).

## Изолированная автоматическая приёмка Auth

[Запуск локального Auth lab](development.md#локальная-приёмка-auth-и-подписки)
проверяет настоящий `App`, установленный SDK, GoTrue, SMTP Mailpit и
PostgREST/RLS. Два владельца создаются через signup/письма, а не SQL-вставку
в `auth.users`; пользовательские JWT выдаёт GoTrue. `.env` и production-ключи
не читаются. БД новая, исходная локальная БД и старые лаборатории не сбрасываются.

Проверены регистрация, запрет входа до подтверждения, повтор письма,
подтверждение, создание заведения с потерей успешного ответа после commit,
reload/retry без дубля, обновление JWT и вход с новым паролем. Проверки
восстановления включают использованные/повреждённые/просроченные ссылки,
перезагрузку формы, вход другого аккаунта, переключение/выход в другой вкладке.
Простое `?auth=recovery` права на изменение пароля не даёт.

Счёт создаётся в реальном UI под JWT владельца, без выдачи продукта.
Попытка владельца вызвать `record_provider_payment` через HTTP запрещена
именно правами (`42501`); только серверная **локальная имитация** подтверждения
делает счёт оплаченным и обновляет доступ в кабинете. Другой владелец не видит
чужой счёт и не получает этот доступ. Кнопки симуляции в production UI нет.

Границы: default-шаблоны и loopback redirect стенда, не production-настройки;
SMTP до Mailpit, не доставка через внешнего провайдера/спам-фильтры;
серверная имитация оплаты, не webhook платёжной компании. Для истечения
письма сдвигается `recovery_sent_at` только синтетического пользователя:
проверяет реальный GoTrue, но час ожидания и часы ОС не воспроизводятся.
Поведение POS/device, терминала T2 и полный набор multi-location API — отдельно.

## Сессии и ограничения реализации

Клиент явно использует implicit flow. SDK проверяет callback, а контроллер
подписывается на Auth-события до завершения его инициализации. Только
`PASSWORD_RECOVERY` запускает новый recovery-процесс: параметр
`?auth=recovery` сам по себе не доказывает пригодность ссылки. Ошибка
callback не должна открывать кабинет ранее вошедшего пользователя.
См. [implicit flow](https://supabase.com/docs/guides/auth/sessions/implicit-flow)
и [Auth events](https://supabase.com/docs/reference/javascript/auth-onauthstatechange).

- В `sessionStorage` записываются только ID аккаунта и время начала recovery,
  не пароль и не копии токенов. SDK продолжает штатно хранить свою сессию.
  UI-метаданные не являются серверной границей авторизации.
- Форма действует 15 минут с verified recovery-события и только для того же
  аккаунта. Это срок формы, **не** настройка срока письма на сервере.
  Перезагрузка сохраняет форму в этой вкладке; при недоступном хранилище
  может потребоваться новая ссылка. Auth-параметры удаляются из URL после
  обработки SDK; произвольный адрес `next` не используется.
- Сохранение пароля привязано к исходной recovery-сессии через отдельный
  Auth-клиент без persistence и автообновления. Он сверяет ID аккаунта и
  освобождается после операции. Переключение основной вкладки на другого
  пользователя не должно направить сохранение на нового пользователя.
  Истёкший или близкий к истечению токен требует свежей ссылки.
- На сохранение отводится 30 секунд. Timeout означает **неизвестный исход**,
  а не доказанный отказ сервера: повторное сохранение через прежнюю форму
  закрывается; предлагается вход с новым паролем либо новое письмо.
- Загрузка сессии и контекста ограничена таймаутами по 15 секунд на запрос.
  Ошибки имеют повтор. При смене пользователя/выходе контекст очищается
  немедленно, поздний ответ старого запроса отбрасывается.
- Выход использует `scope: local`; это не обещание отзыва всех сессий на
  остальных устройствах. Отказ выхода показывается явно с повтором.

Реализация: [формы](../backoffice/src/AccountAuth.jsx),
[контроллер](../backoffice/src/account-session.js),
[инициализация SDK](../backoffice/src/supabase.js),
[состояния приложения и onboarding](../backoffice/src/App.jsx).
SQL и серверная модель доступа этим изменением не меняются.

## Создание заведения без дублей (A4, схема 165)

Кабинет вызывает `create_digital_workspace` с клиентским UUID запроса,
именем организации/точки и выбранными digital-продуктами. RPC одной
транзакцией создаёт организацию, точку, owner-членство, заявки и приватную
квитанцию запроса. Это **не** оплата, триал или активация подписки.

- Повтор того же UUID и нормализованных данных возвращает прежний результат.
  Другой payload или аккаунт не могут воспользоваться чужой квитанцией.
- Все bootstrap-пути сериализованы блокировкой строки `auth.users`:
  две вкладки, старый клиент и POS не создают две организации одному аккаунту.
  Старые RPC сохраняют сигнатуры и ошибку повторного bootstrap.
- При потере ответа форма сохраняет в `sessionStorage` UUID, названия и
  выбранные продукты **для текущего аккаунта**. Паролей/токенов в записи нет.
  Поля замораживаются; **Check and continue** повторяет исходный запрос.
  При недоступном хранилище повтор в открытой форме работает, после перезагрузки
  от дубля дополнительно защищает серверная привязка аккаунта.
- Перед записью клиент проверяет свежий `getUser`; если организация уже есть,
  создание не повторяется. RPC привязан явным Authorization к исходной сессии.
  Ответы после смены пользователя/закрытия формы не запускают продолжение.
- После создания отдельно обновляется JWT. Ошибка refresh не выдаётся за
  ошибку создания: предлагается продолжить открытие существующего заведения.
  Ожидания ограничены по 15 секунд на запрос; timeout не доказывает откат.
- Без миграции 165 показано требование обновить сервер. Автоматического
  отката к старому, неидемпотентному RPC нет. **Сначала миграция, затем кабинет**;
  Для A4 требовалась схема 165; следующий checkout A5 требует 166.
  Актуальный минимум указан в Kassa `schemaVersion.ts`; факт применения в
  production записывается в журнале (165–167 выпущены 13.09.2026).

Исходники: [клиентский сценарий](../backoffice/src/workspace-setup.js),
[миграция 165](../../kassa/supabase/migrations/165_workspace_onboarding_idempotency.sql),
[SQL-регрессии](../../kassa/supabase/tests/workspace_onboarding.test.sql),
[конкурентный тест](../../kassa/scripts/test-onboarding-concurrency.mjs).
Квитанция не восстанавливает удалённое заведение или отозванное owner-членство.

## Живая приёмка перед закрытием A1–A3

Ниже — приёмка согласованной целевой среды и **внешней** доставки писем.
Локальные 23 сценария выше не проставляют эти отметки автоматически.

- [ ] Зафиксировать сборку, тестовый аккаунт, настройки redirect/шаблонов и SMTP.
- [ ] Зарегистрировать обычного владельца; письмо приходит; подтверждение
  открывает onboarding; повторная отправка и уже использованная ссылка понятны.
- [ ] Войти, выйти, запросить reset; получить письмо; открыть ссылку и сохранить
  новый пароль; повторный вход успешен, старый пароль отвергается.
- [ ] Повторить ссылку, дождаться серверного истечения, открыть повреждённую
  ссылку и открыть её при ранее вошедшем другом аккаунте.
- [ ] Перезагрузить recovery-форму; проверить смену аккаунта в другой вкладке,
  обновление токена и отсутствие отображения данных предыдущего владельца.
- [ ] Проверить отключённую сеть при запросе письма, сохранении пароля,
  чтении контекста и выходе; после восстановления связи доступен понятный путь.
- [ ] Записать фактические результаты без токенов, паролей и полных email-ссылок.

Создание организации без дублей (A4) проверено локально по SQL/UI и в новом
сквозном GoTrue/PostgREST lab, включая потерю ответа после commit и reload.
Базовый месячный checkout и локальная имитация подтверждения оплаты (A5)
описаны в [биллинге](../../kassa/docs/billing.md). Локальный общий Auth-контур
проверен выше, но это не приёмка реального провайдера. Изоляция пакетов (A6)
принимается отдельно. Наличие формы входа не закрывает эти задачи.

## Границы digital-аккаунта и продуктов (A6, 168)

Для digital-сессии (JWT без `location_id`) активное членство проверяется
внутри `auth_org_id()` на каждом серверном запросе. Старый подписанный токен
не сохраняет доступ после деактивации/удаления членства: tenant RLS и RPC
получают NULL вместо организации. Устройство POS с `location_id` — отдельная
существующая модель доступа, а не digital-аккаунт. Отзыв веб-членства такого
совмещённого аккаунта **не равен** отзыву device/PIN-доступа; 168 не вводит
строгий режим горячего POS-потока и не меняет offline outbox.

Матрица ниже относится к активному обычному digital-владельцу, двум разным
организациям и одной точке в каждой. «Нет» означает серверный отказ/пустое
RLS-чтение, не только отсутствие пункта навигации.

| Доступ | Каталог: чтение/изменение | Чтение Orders | Чтение Reserve | Своя история подписок |
|---|---|---|---|---|
| Нет активного продукта / срок истёк | Нет | Нет | Нет | Да |
| Menu-only | Да | Нет | Нет | Да |
| Orders-only | Да, Menu отдельно не нужен | Да | Нет | Да |
| Reserve-only | Нет | Нет | Да | Да |
| Членство отозвано/удалено | Нет | Нет | Нет | Нет |

- Catalogue RPC, прямые таблицы и связанные варианты/модификаторы защищены
  capability; для прямой записи web-роль должна быть owner/manager.
  Accountant сохраняет разрешённые чтения, но не получает manage через REST.
- Нельзя связать свою категорию с чужой точкой, товар с чужой категорией/
  станцией, вариант с чужим товаром или модификатор с чужой группой.
  Серверный триггер проверяет и прямые записи, и SECURITY DEFINER RPC.
- Прямые чтения Orders/Reserve и их событий дополнительно проверяют capability
  в точке. Существующие tenant-политики остаются обязательными.
- Счета/подписки не удаляются при истечении продукта. Чужой фискальный экспорт
  запрещён; собственный экспорт остаётся отдельным разрешённым серверным путём,
  не зависящим от покупки продукта.
- `menu-images` — намеренно публичные гостевые изображения. Запись проверяет
  организацию, роль и активный продукт. Reserve разрешено загружать собственное
  оформление без покупки Menu; публичность готовых изображений не менялась.
- Кабинет связывает загрузку контекста с исходным access token и не принимает
  ответ другой организации. Выход, смена аккаунта/организации и ошибка повторной
  проверки доступа убирают старый экран; поздние ответы не возвращают его.

Проверки: `kassa/supabase/tests/account_product_boundaries.test.sql`,
`backoffice/test/account-access.test.mjs` и unit-тесты контроллера аккаунта.
Для отдельного реального PostgREST/JWT-прогона из `anglesite/`:

```bash
node scripts/test-account-access-http.mjs angle_billing_lab_a6_<new_suffix>
```

Нужны локальный Docker и запущенные контейнеры `supabase_db_kassa`/
`supabase_rest_kassa`. Скрипт создаёт новую маркированную синтетическую БД,
берёт только локальный PostgREST image/DB transport, выпускает временные JWT
с новым ключом и открывает порт только на localhost. `.env` и production не
используются. Временный HTTP-контейнер удаляется в finally, БД сохраняется;
повтор требует нового имени. Это настоящая проверка подписи JWT и RLS через
HTTP, но токены выпущены тестом, **не GoTrue**. Регистрацию/локальную почту
отдельно проверяет Auth lab выше; внешняя почта и реальный provider ещё не
приняты. Не считать эти сценарии полным
аудитом всех RPC, POS-ролей или multi-location-подписок. Результаты и состояние
production — в [журнале](verification-log.md).
