# Согласованный выпуск ANGLE + Kassa

Статус: рабочий checklist от 13.09.2026, не журнал выполненного релиза.
Подробный runbook Supabase, POS, service worker и APK остаётся в
[Kassa deployment](../../kassa/docs/deployment.md).

## 0. Обязательный gate перед клиентским запуском — F5

**OPEN. Без закрытого F5 нельзя подключать первое заведение с реальными
операциями — даже в бесплатном пилоте.** Технические публикации и изолированная
разработка могут продолжаться; они не означают готовность к продажам.
Если реальные операции уже идут, защиту нельзя откладывать до первого платежа.
Владелец планирует оплатить инфраструктуру перед продажами; сама оплата не
заменяет проверку ниже. Источник статуса — [план F5](product-completion-plan.md),
процедура — [бэкапы и восстановление](../../kassa/docs/backups.md).

- [ ] Владелец включил согласованную платную инфраструктуру; нужные backup/PITR
  настройки проверены фактически, не предполагаются по названию тарифа.
- [ ] Автоматическая защита БД обеспечивает RPO ≤15 минут; проверены последняя
  доступная точка/копия, срок хранения и защита от потери основного проекта/Mac.
- [ ] Файлы Storage копируются отдельно; восстановлены файлы и ссылки на них.
- [ ] Настроены контроль просроченной копии/сбоя, оповещение и ответственный.
- [ ] На актуальной версии пройден полный изолированный drill: данные,
  конфигурация, Auth и выбранный клиентский сценарий восстановлены за ≤1 часа;
  финансовые инварианты и права проверены. Учебный restore не выполняется в production.
- [ ] Доказательства и ограничения записаны в журнал; F5 явно переведён в CLOSED
  только после всех проверок. Локальный SQL-restore 13.09 сам по себе не закрывает gate.

## 1. Зафиксировать объём и среду

  затронутые продукты и окружение в [журнале](verification-log.md).
- [ ] Определено, меняются ли SQL, Edge Functions, кабинет, POS, гостевая

- [ ] Проверены целевой Supabase project ref, публичные URL/ключи и Vercel-

- [ ] Проверены backup и возможность восстановления; при изменении данных
  согласованы точка восстановления и допустимые потери. Старый restore-test
  не доказывает восстановимость текущей схемы.

## 2. Проверить код и совместимость

Из `anglesite/`:

```bash
npm ci
npm test
npm run build
npm run check:docs
```

`npm test` = `test:unit` + `test:browser`; браузер обязателен, пропуск возможен
только явным `ANGLE_BROWSER=optional` и для выпуска не годится. Те же шаги
выполняет [CI](../.github/workflows/ci.yml) на push в `main`/`codex/**` и PR — сверьте, что для
выпускаемого коммита прогон CI зелёный: локальный прогон его не заменяет.

Шаг `check:docs` сохраняем. Перед каждым push проверить, что новые рабочие
инструкции, индексы и все документы/ресурсы, на которые они ссылаются,
включены в подготавливаемый коммит. Документационная основа D0 закоммичена;
наличие нового файла локально не означает, что он попадёт в checkout CI. Не добавлять
все untracked-файлы вслепую: исходные видео и посторонние черновики не становятся
частью релиза автоматически. Межрепозиторные ссылки CI без Kassa пропускает
явно; совместная локальная проверка — `npm run check:docs -- --require-kassa`.

До готовности целевой БД отправлять связанные изменения в рабочие ветки
`codex/**` обоих репозиториев. Они запускают CI, не меняя `main`;
в Kassa `main` связан с production-деплоем Vercel. Возможный Vercel Preview
не считать тестовой средой без проверки его env/изоляции БД и не выполнять
там тестовые мутации. Merge/deploy — отдельный шаг после необходимых gates.

Из `kassa/`:

```bash
npm ci
npm run lint
npm run check:schema
npm run test:all
npm run build
npm run check:bundle
```

При изменении гостевой поверхности отдельно проверить `npm run build:menu`.
Обновление общих зависимостей сборки также требует обеих сборок. Текущий
`check:bundle` считает весь статический startup-граф modern и legacy,
включая modulepreload, polyfills и транзитивные статические импорты.
После F2 появились `jsx-runtime` modern/legacy; проверить их загрузку,
обновление service worker и повторный офлайн-старт по T2 checklist.
POS и Menu — разные сборки одного репозитория; обе используют `dist/`, поэтому
их артефакты нельзя путать или выпускать из одного последовательно перезаписанного
каталога как два одинаковых приложения. На сервере используются отдельные сборки.

SQL и права проверить в **локальной изолированной** Supabase через
[pgTAP-инструкцию](../../kassa/supabase/tests/README.md). `supabase db reset`
не является командой обслуживания production.

- [ ] Последняя миграция Kassa согласована с `MIN_SCHEMA_VERSION` и реальной
  схемой целевой базы. `check:schema` проверяет файлы, не состояние удалённой БД.
- [ ] Перед 169: свежий закрытый backup и read-only сверка devices/Auth/locations
  (нет чужих связей, необъяснённых отсутствующих Auth-user или конфликтов
  `(org,device_uuid)`). Активные привязки не исправлять массовой перепривязкой;
  выполнить [A6.2 T2 smoke, 0.1](../../kassa/docs/t2-smoke-test.md). Сначала
  миграция, затем клиент с `MIN_SCHEMA_VERSION=169`; результаты — в журнал.
- [ ] Проверены используемые кабинетом RPC/колонки. SchemaGuard POS не
  является автоматической проверкой совместимости кабинета.
- [ ] Перед170: сохранён актуальный закрытый backup; новая схема проверена
  локальным pgTAP и отдельным конкурентным тестом телеметрии. Сначала170,
  затем клиент с `MIN_SCHEMA_VERSION=170`. На обычном зарегистрированном
  устройстве диагностика принимается; до регистрации отказ оставляет пакет
  в клиентской очереди. Не создавать синтетические события в production
  без отдельно выделенного тестового контекста.170 не закрывает серверную
  privacy/ретенцию и не является гарантией удаления логов через30 дней.
- [ ] Для нового onboarding применена миграция 165 (`create_digital_workspace`)
  **до** выпуска кабинета. Legacy RPC совместимы; при отсутствии нового RPC
  клиент останавливает создание с требованием обновить сервер, не обходит защиту.
- [ ] Для экрана подписок применена миграция 166. Self-service по умолчанию
  disabled; production не переводится в test. Локальные `billing-lab.mjs` и
  `test-billing-lab.mjs` не являются частью публикации и не разворачиваются
  как публичные сервисы. Цены и реальный провайдер требуют отдельной приёмки.
- [ ] Браузерные наборы действительно выполнялись: в отчёте прогона нет строк
  `SKIP no browser for puppeteer`, а число выполненных тестов совпадает с
  полным прогоном. Выпуск по результату с `ANGLE_BROWSER=optional` запрещён.
- [ ] Сценарии изменения проверены на обычном аккаунте, а не только developer;
  для прав доступа — отрицательные проверки чужой организации.

Старые ссылки на миграции 088–105 описывают появление кабинета и capability-
модели, а не достаточную схему сегодняшнего клиента. Не заменяем старое число
новым константным числом в инструкциях: источники —
[миграции](../../kassa/supabase/migrations/) и
[schemaVersion.ts](../../kassa/src/lib/schemaVersion.ts).

## 3. Выпустить по зависимостям

1. Применить согласованные миграции **до** клиентов, вызывающих новый API.
   Production-команды Kassa используют project-ref guard (`db:push`,
   `functions:deploy`). Guard не обходить, несовпадение ref — остановка.
2. Выпустить изменённые Edge Functions, проверить их ответы и ошибки.
3. Выпустить затронутые сборки: POS, публичную Menu и сайт с кабинетом.
   Для сайта — `npm run build`, output `dist`; для гостевой Kassa —
   `npm run build:menu` / `VITE_APP_SURFACE=menu` согласно настройке проекта.
4. Если менялся Android-мост, origin или конфигурация APK — собрать и принять
   новый APK по [инструкции](../../kassa/docs/android-printing.md).

Публикация не выполняется «для проверки документации». Удалённые операции
делаются только в согласованном релизе. Не активировать продукты и не
отправлять тестовые сообщения реальным клиентам в ходе smoke-test.

## 4. Приёмка после выпуска

- [ ] Сайт и `/account/` открываются; сценарий входа и выбранный продукт работают.
- [ ] Обновляются контекст кабинета и гостевые данные после изменения настроек.
- [ ] Публичные меню/заказ/бронь проверены для затронутых продуктов.
- [ ] Старая открытая вкладка переживает обновление chunks и сессии.
- [ ] POS при его изменении принят на устройстве: PIN, смена, продажа, чек,
  offline/replay и безопасное обновление — [T2 checklist](../../kassa/docs/t2-smoke-test.md).
- [ ] Результат, пропуски и ограничения записаны в журнал. Отложенные платежи
  и налоговая регистрация не помечены выполненными.

Recovery-сценарий и фактическая доставка письма добавляются в обязательную
приёмку после реализации A1–A3. До этого блок аккаунтов остаётся открытым.

## 5. Откат

Заранее сохранить идентификаторы предыдущих frontend deployments и определить,
совместимы ли они с новой схемой. Откат frontend не откатывает БД. SQL исправляется
новой миграцией; восстановление данных — отдельная операция с оценкой потерь и
согласованием, не универсальная кнопка отмены релиза.

Не очищать outbox, Storage или данные организации ради устранения ошибки.
Порядок разбора: [offline](../../kassa/docs/offline.md),
[deployment](../../kassa/docs/deployment.md), [backups](../../kassa/docs/backups.md).
