## 2. Прод против исходников

### Кабинет `angle.co.il/account`

Прод отдаёт `/account/assets/index-BzJciHUX.js` (725 992 Б) и
`index-BWW-4vmC.css` (73 963 Б), `last-modified: 2026-08-02 04:35 UTC`.

Хеш JS отличается от локальной сборки, потому что Vite инлайнит
`VITE_SUPABASE_*`, а локально их нет. Чтобы это не осталось догадкой, сборка
повторена с продовыми значениями (взяты из самого прод-бандла — это публичный
anon key):

| | имя файла | SHA-256 |
|---|---|---|
| прод | `index-BzJciHUX.js` | `ca905b41…3caf2d` |
| локальная сборка HEAD с прод-env | `index-BzJciHUX.js` | `ca905b41…3caf2d` |

**Совпадение побайтовое, включая имя файла.** CSS совпадает и без подстановки
(`index-BWW-4vmC.css` в обоих местах). Значит:

- прод кабинета — это ровно текущий `main`;
- расхождений «на проде старая сборка» нет;
- любой дефект, наблюдаемый на проде, — дефект исходников, а не выкладки и не
  service worker.

### Видимость и авторизация

Видимость считается в `navigation.js` из **эффективных capabilities** контекста
(`get_backoffice_context`, миграция 105), с фолбэком на продукты для серверов
до 105:

| Раздел | Условие |
|---|---|
| Dashboard, Locations | всегда |
| Catalogue | `catalog_manage` |
| QR Menu & Online | `public_menu` ∨ `online_orders` ∨ `public_reservations` ∨ `reservations_desk` |
| Orders | `orders_desk` |
| Reservations | `reservations_desk` |
| Sales | `pos_reports` |
| Activity, Team, Customers, Devices | `pos_operate` |
| Reports, Integrations | только `account_type = 'developer'` |

Пустая группа не рендерится. Организация без продуктов получает экран
активации вместо операционных разделов.

Настоящие запреты живут на сервере, тремя слоями:

- RLS по `org_id` из JWT — граница арендатора;
- `require_org_capability(...)` → стабильная ошибка `module_disabled` (14
  использований в миграциях);
- `require_backoffice_or_staff(p_session, p_perm)` — единый гейт записи для
  веба (091, ужесточён 096; 35 использований): роль из JWT (`owner`/`manager`/
  `accountant`), owner не ограничивается уровнями прав, остальные подчиняются
  тем же уровням, что кассовые сотрудники. У кассы свой гейт
  `require_staff_perm` (112 использований).

Скрытый пункт меню — не защита; это в коде записано явно и должно таким
остаться при любой перестройке навигации.

## 6. Скриншоты базовой линии

40 кадров в трёх вьюпортах — 1440×900 (desktop), 1024×768 (tablet), 390×844
(mobile) — для 13 экранов: Dashboard, Orders, Reservations (Timeline / List /
Analytics), Sales, Activity, Customers, Catalogue, Locations, Team, QR Menu &
Online, Devices; плюс мобильная шторка навигации.

Файлы: `screenshots/backoffice/platform-phase0-*.png`, машинный отчёт —
`platform-phase0-report.json` (переполнение, падения, заголовок, высота
документа, ошибки консоли по каждому кадру).

Снималось на локальном стенде: `backoffice/src/App.jsx` рендерится целиком, а
модуль `./supabase` подменяется фикстурами через плагин esbuild. Стенд лежит
в `screenshots/backoffice/stand-platform-phase0/` (тоже вне git) —
`shoot.mjs` (съёмка), `checks.mjs` (проверки пунктов планов), `measure.mjs`
(плотность), `overflow.mjs` (поиск виновника переполнения),
`supabase-stub.js` (данные).

Ограничения, о которых нельзя забывать при чтении кадров:

1. Это **не прод под сессией владельца**: данные выдуманные, объёмы маленькие.
   Живая приёмка на настоящих данных не заменяется этим стендом.
2. Фикстура повторяет форму ответа сервера, а не сам сервер. Расхождение формы
   выглядит как пустое состояние — при первой съёмке так и случилось с
   `sales_report` (ключи `summary.*`), фикстура исправлена.
3. Не покрыты формы аккаунта, кроме developer (у него видны все разделы,
   включая `planned`). Матрицу POS-only / Menu-only / Orders / Reserve
   снимать заново не стали: она снята в Phase 2 старого плана
   (`phase2-shape-*.png`) и закреплена тестами `navigation.test.js`.

   месту десять раз, таблица данных как примитив отсутствует. Мастер-план
   требует DataTable, Drawer, ConfirmationDialog и т.д. — их придётся строить,
   а не консолидировать.
4. **12 нативных `confirm`/`prompt`/`alert`** в 5 файлах — блокирующие
   браузерные диалоги вместо продуктового подтверждения.
5. **Доступность диалогов.** Фокус-ловушки нет нигде; `Escape` обрабатывают
   `App` (Help, меню аккаунта), `BookingForm`, `OrdersInbox` — остальные семь
   не закрываются с клавиатуры. `role="tablist"` объявлен в 8 местах, стрелки
   не работают ни в одном.
6. **Плотность десктопа.** Заголовок каждой страницы — 107–118px, `h1` 40–50px;
   первая рабочая поверхность начинается на 264–513px от верха при высоте окна
   900px (худший случай — Sales: больше половины первого экрана до первой
   цифры).
7. **Dashboard не отвечает на вопрос «что сейчас».** Сегодня это три счётчика
   (точки, команда, устройства), список точек, быстрые действия и карточка
   продуктов. Ни «сегодня», ни «требует внимания», ни смены, ни офлайн-касс,
   ни неопубликованных изменений — то есть весь Phase 3 мастер-плана впереди.
8. **Каталог открывается свёрнутым.** По умолчанию видны только строки
   категорий: на десктопе 1440×900 это две строки и пустой экран под ними.
   Мастер-план требует компактную рабочую поверхность по умолчанию.
9. **Английский зашит в разметку**, RTL нет. Для израильского клиента это
   ограничение продаж, а не косметика.
10. **Один бандл на 726 kB** без разделения — мастер-план (Phase 11) требует
    ленивую загрузку крупных модулей.

## 9. Риски и открытые вопросы

1. **Применение миграции 134 на проде не подтверждено.** Нужен владелец или
   доступ к БД. Пока это дыра в цепочке доказательств по воронке броней.
2. **Живой приёмки владельцем не было** ни по Phase 6b (клиенты), ни по
   Phase 7 (отчёты), ни по правкам аудита 02.08. Стенд и автотесты её не
   заменяют.
3. **Нет линтера и typecheck** в `anglesite`. Мастер-план ссылается на
   «configured lint/typecheck» — их надо либо завести, либо честно писать в
   отчётах, что проверок две (`test`, `build`).
4. **Один общий stylesheet** — главный источник риска для фазы дизайн-системы:
   любая правка `styles.css` касается всех 13 разделов сразу. Миграцию на
   токены надо вести так, чтобы каждая порция была отдельно проверяемой.
5. **SPA-фолбэк кассы отдаёт 200 на несуществующие ассеты.** Проверять
   выкладку кода ответа нельзя — только манифест `sw.js` или содержимое.
6. **Прод и `main` сейчас совпадают побайтово.** Это ценное свойство: пока оно
   держится, «у меня иначе» означает кэш браузера у конкретного человека, а не
   расхождение веток. Стоит проверять его тем же способом перед каждым
   разбором инцидента.
