# Как поддерживать документацию

Правила введены 13.09.2026 для `anglesite` и `kassa`.

## Один источник для каждого вопроса

| Информация | Где поддерживать |
|---|---|
| Объём, приоритеты, критерии завершения | [План завершения](product-completion-plan.md) |
| Связи репозиториев и продуктов | [Обзор системы](system-overview.md) |
| Запуск сайта/кабинета | [Разработка ANGLE](development.md) |
| SQL, RLS, API, POS, offline, Android | соответствующий документ [Kassa](../../kassa/docs/README.md) |
| Общий выпуск и проверки совместимости | [Release checklist](release-checklist.md) |
| Результаты конкретного прогона | [Журнал проверок](verification-log.md) |
| Почему когда-то изменили дизайн/архитектуру | [История решений](archive/README.md) |

README — навигация и быстрый запуск. AGENTS — устойчивые правила разработки,
не дневник релизов и не копия всех маршрутов. Не заводить второй master plan
с именем инструмента или автора; изменять текущий план.

## Статусы не смешивать

- Рабочая инструкция: что делать сейчас, источник в коде и дата сверки.
- Справочник: как устроен модуль; исторические дополнения явно датировать.
- План: ещё не сделано; критерий завершения и зависимость от других задач.
- Checklist: что проверить; пустой пункт не доказывает наличие дефекта.
- Журнал: что действительно проверено, где, на какой версии и с каким результатом.
- Архив: контекст прежнего этапа, не текущая инструкция к релизу.

Если дата или статус production неизвестны, написать «не проверено», а не
обновлять дату старого утверждения. «Есть в коде», «прошло тест» и «работает
у клиента» — разные уровни подтверждения.

## Обязательное обновление вместе с изменением

1. При изменении функции обновить её основной справочник, примеры и checklist.
2. При изменении env, RPC, маршрутов или порядка выпуска — исправить рабочие
   инструкции обоих затронутых репозиториев.
3. Удалённую функцию убрать из актуальной инструкции; причины оставить в истории.
4. Вносить результат проверки в журнал с версией, средой и ограничениями.
5. Новый документ включать в индекс; новую рабочую инструкцию — также в список
   проверяемых файлов `scripts/check-docs.mjs`. Перемещение — с исправлением ссылок;
   пользовательские черновики не удалять и не переписывать как «мусор».
6. Перед завершением — `npm run check:docs` и `git diff --check`.

Версии пакетов берём из `package.json`/lock-файла, версию схемы — из миграций
и `schemaVersion.ts`. Копировать их в каждый справочник не нужно. Конкретный
номер нужен в журнале испытания или историческом объяснении, не как вечная
инструкция установки. Пароли, токены, дампы и персональные данные в docs не хранить.

## Граница автоматической проверки

`scripts/check-docs.mjs` проверяет существование относительных Markdown-ссылок
в новых рабочих документах/индексах и наличие каждого Markdown-файла `docs/`
в индексе своей категории. При наличии соседней Kassa также проверяются её
README, AGENTS, индекс, инструкции биллинга, бэкапов и разработки. Если Kassa
отсутствует, внешние ссылки явно пропускаются;
для обязательной совместной проверки: `npm run check:docs -- --require-kassa`.

Проверка не обращается в интернет, не проверяет anchors, свободно написанные
пути, содержимое старых архивных документов и смысл инструкций. Это защита
навигации, не замена сверке кода. Основа D0, индекс и связанные документы
закоммичены. При добавлении новых страниц нужно включать в коммит и связанные
ресурсы: локальные untracked-файлы отсутствуют в checkout CI.

## Что ещё систематизировать по ходу завершения

Большие справочники заказов/броней/БД содержат поэтапные дополнения. При работе
над блоками A–F переносить подтверждённое текущее поведение в основные разделы,
а устаревшие детали — в историю. Не считать их целиком выверенными только из-за
нового индекса. Краткие инструкции для владельца и персонала готовить на уже
принятом сценарии перед пилотом, чтобы не документировать ещё меняющийся UI.
